# Безопасность safe-accounts

Как устроена защита данных и что делать при инцидентах. Норматив — `AGENTS.md`;
подтверждение мер тестами — `docs/security-checklist.md`; полный разбор рисков —
`docs/threat-model.md`.

## Как защищены пароли пользователей

- Пароли пользователей хранятся **только** в виде Argon2id-хэша
  (параметры m=64 МиБ, t=3, p=1) в колонке `users.password_hash`.
  Plaintext-пароль нигде не сохраняется — ни в БД, ни в логах, ни в аудитах
  (запрещено `AGENTS.md` §7–8 и проверено тестами `SecurityChecksIT.*`).
- Минимальная длина — 12 символов; валидация — `jakarta.validation`
  на DTO + повторная проверка в сервисном слое.
- Проверка пароля — константновременное сравнение Argon2id-верификацией.
- При смене пароля (`POST /api/me/password`) и admin-сбросе
  (`POST /api/admin/users/{id}/reset-password`) все прочие Bearer-токены
  пользователя отзываются.

## Как защищены токены доступа

- Аутентификация API — Bearer-токен: `sat_` + base64url, ≥ 256 бит энтропии
  из `SecureRandom`, срок жизни 24 ч.
- В БД (`auth_tokens.token_hash`) хранится **только SHA-256 хэш** токена;
  сырой токен показывается клиенту **один раз** при выпуске и нигде
  не хранится в восстановимом виде.
- Ревокация и отзыв: `POST /api/auth/logout` отзывает текущий токен;
  смена пароля отзывает все остальные токены; admin-сброс пароля отзывает
  все токены пользователя. Отозванный токен отклоняется (тесты
  `SecurityChecksIT.revokedTokenDoesNotWork`).
- Веб-интерфейс Bearer-токены не использует: серверные HTTP-сессии
  (HttpOnly cookie) + CSRF-защита; токены не попадают в браузерное хранилище.
- Rate limiting по IP на `POST /api/auth/login|register` (по умолчанию
  10 запросов/60 с, `429` + `Retry-After`) и блокировка аккаунта на 15 минут
  после 5 неудачных входов затрудняют перебор.

## Как шифруются записи сейфа

Ключевая иерархия: **KEK → DEK → данные**.

1. Каждому пользователю при регистрации генерируется собственный **DEK**
   (AES-256).
2. DEK хранится в БД **только wrapped**: зашифрованным мастер-ключом **KEK**
   (AES-256-GCM; `users.dek_wrapped`, `dek_iv`, `dek_kek_id`).
3. Каждое чувствительное поле записи сейфа (сайт, логин, пароль, примечание)
   шифруется DEK владельца **AES-256-GCM**; IV — 12 байт из `SecureRandom`,
   уникальный на каждую операцию (никаких ECB/детерминированных IV;
   unit-тесты `AesGcmCryptoServiceTest`, `KeyManagerTest`).
4. В БД plaintext отсутствует (`vault_entries.*_enc`); списки записей
   пароли не возвращают — расшифровка только в явном детальном запросе
   `GET /api/vault/{id}?reveal=true` при наличии прав, каждый reveal
   фиксируется аудитом (`SECRET_REVEALED`).
5. KEK задается только из окружения/файлов секретов; без него приложение
   падает на старте. В логах — только key id и усеченный fingerprint,
   материал ключей никогда не логируется.
6. Поддерживается ротация KEK с перепаковкой DEK
   (`POST /api/admin/crypto/rewrap-deks`) — `docs/key-rotation.md`.
7. Доступ к записям — только владельцу; чужая запись неотличима от
   несуществующей (единый 404, тесты `E2eFlowIT.*`). Административные
   операции — только роль `ADMIN` (SecurityConfig + `@PreAuthorize` +
   проверка в сервисе).

Ошибка расшифровки возвращает нейтральный ProblemDetail (RFC 7807) без
деталей; стектрейсы клиентам не возвращаются.

## Что делать при утечке (БД / логов / данных)

Определите источник, затем действуйте по `docs/threat-model.md`
(матрица реагирования). Кратко:

**Утечка дампа БД.**

1. Дамп сам по себе не раскрывает секреты (только шифротекст), но инцидент:
   ограничьте распространение, зафиксируйте факты.
2. Выполните **ротацию KEK** (`docs/key-rotation.md`): новый ключ →
   перезапуск → `POST /api/admin/crypto/rewrap-deks`. После перепаковки
   украденный дамп окончательно бесполезен для новых данных.
3. Отзовите все пользовательские токены (сброс паролей администратором).
4. Расследуйте канал утечки; пересмотрите шифрование бэкапов (`age`/`gpg`,
   `docs/backup-restore.md`).

**Утечка логов.**

1. Логи не содержат секретов по построению (запрещено и подтверждено
   тестами; `SensitiveDataMasker` — последний рубеж), но проверьте выгрузку
   на неожиданные артефакты (stack trace с данными, отладочные строки).
2. Ревизия того, куда и кто имеет доступ к системе логирования; те же
   требования хранения, что к БД.
3. Если в логах все же найден секрет (например, кто-то нарушил правило) —
   считайте его скомпрометированным: смените соответствующий пароль/ключ.

**Утечка файла секрета на хосте** — см. следующий раздел
(компрометация KEK) или смену пароля БД (`POSTGRES_PASSWORD` +
`docker compose up -d db` + перезапуск app).

## Что делать при компрометации мастер-ключа

Это максимальный по ущербу инцидент: держатель KEK + дамп БД может
расшифровать все записи. Действовать немедленно:

1. **Изолировать**: ограничить доступ к хосту/хранилищу, где жил ключ;
   не удалять скомпрометированный ключ из конфигурации до перепаковки DEK.
2. **Аварийная ротация KEK** (детали — `docs/key-rotation.md`,
   раздел «Аварийная ротация»):
   - сгенерировать новый KEK (`./scripts/generate-master-key.sh`);
   - добавить его в конфигурацию как активный
     (`APP_CRYPTO_KEYS_<N>_ACTIVE=true`), старый оставить как
     `ACTIVE=false` только для расшифровки;
   - перезапустить приложение;
   - `POST /api/admin/crypto/rewrap-deks` — перепаковать все DEK;
   - убедиться в чтении контрольных записей (`reveal=true`).
3. **Отозвать все токены** пользователей (admin-сброс паролей) — компрометация
   KEK часто сопровождает более широкую компрометацию хоста.
4. **Сменить пароль БД** и проверить целостность данных/аудита на предмет
   посторонних действий (вдруг KEK украли вместе с доступом к API).
5. **Бэкапы**: дампы, снятые до ротации, остаются читаемыми с украденным
   KEK — пересмотреть их хранение/сроки или перешифровать хранилище бэкапов.
6. Расследование: источник утечки ключа (логирование, дампы памяти,
   доступ администраторов, утечка из хранилища секретов) и закрытие канала.
7. Аудит ротации: `KEY_ROTATION_STARTED/COMPLETED/FAILED` — убедиться,
   что перепаковка прошла полностью (`rewrappedUsers: 0` при повторном
   вызове).

## Смежные правила (кратко)

- Ошибки API — RFC 7807 ProblemDetail без стектрейсов.
- Все входные данные валидируются `jakarta.validation`.
- Секреты — только из env/файлов секретов/KMS; в коде, репозитории,
  миграциях и артефактах сборки их нет.
- Аудит фиксирует вход/неудачный вход, выпуск/отзыв токена, операции над
  записями, админ-действия и ротацию ключей — без секретов.
