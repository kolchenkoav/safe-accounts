# Безопасность safe-accounts

Как устроена защита данных и что делать при инцидентах. Норматив — `AGENTS.md`;
подтверждение мер тестами — `docs/security-checklist.md`; полный разбор рисков —
`docs/threat-model.md`.

## Как защищены пароли пользователей

- Пароли пользователей хранятся **только** в виде Argon2id-хэша
  (параметры m=64 МиБ, t=3, p=1) в колонке `users.password_hash`.
  Plaintext-пароль нигде не сохраняется — ни в БД, ни в логах, ни в аудитах
  (запрещено `AGENTS.md` §7–8 и проверено тестами `SecurityChecksIT.*`).
- Минимальная длина — 12 символов; валидация — `jakarta.validation`
  на DTO + повторная проверка в сервисном слое.
- Проверка пароля — константновременное сравнение Argon2id-верификацией.
- При смене пароля (`POST /api/me/password`) и admin-сбросе
  (`POST /api/admin/users/{id}/reset-password`) все прочие Bearer-токены
  пользователя отзываются.

## Как защищены токены доступа

- Аутентификация API — Bearer-токен: `sat_` + base64url, ≥ 256 бит энтропии
  из `SecureRandom`, срок жизни 24 ч.
- В БД (`auth_tokens.token_hash`) хранится **только SHA-256 хэш** токена;
  сырой токен показывается клиенту **один раз** при выпуске и нигде
  не хранится в восстановимом виде.
- Ревокация и отзыв: `POST /api/auth/logout` отзывает текущий токен;
  смена пароля отзывает все остальные токены; admin-сброс пароля отзывает
  все токены пользователя. Отозванный токен отклоняется (тесты
  `SecurityChecksIT.revokedTokenDoesNotWork`).
- Веб-интерфейс Bearer-токены не использует: серверные HTTP-сессии
  (HttpOnly cookie) + CSRF-защита; токены не попадают в браузерное хранилище.
- Rate limiting по IP на `POST /api/auth/login|register` (по умолчанию
  10 запросов/60 с, `429` + `Retry-After`) и блокировка аккаунта на 15 минут
  после 5 неудачных входов затрудняют перебор.

## Как шифруются записи сейфа

Ключевая иерархия: **KEK → DEK → данные**.

1. Каждому пользователю при регистрации генерируется собственный **DEK**
   (AES-256).
2. DEK хранится в БД **только wrapped**: зашифрованным мастер-ключом **KEK**
   (AES-256-GCM; `users.dek_wrapped`, `dek_iv`, `dek_kek_id`).
3. Каждое чувствительное поле записи сейфа (сайт, логин, пароль, примечание)
   шифруется DEK владельца **AES-256-GCM**; IV — 12 байт из `SecureRandom`,
   уникальный на каждую операцию (никаких ECB/детерминированных IV;
   unit-тесты `AesGcmCryptoServiceTest`, `KeyManagerTest`).
4. В БД plaintext отсутствует (`vault_entries.*_enc`); списки записей
   пароли не возвращают — расшифровка только в явном детальном запросе
   `GET /api/vault/{id}?reveal=true` при наличии прав, каждый reveal
   фиксируется аудитом (`SECRET_REVEALED`).
5. KEK задается только из окружения/файлов секретов; без него приложение
   падает на старте. В логах — только key id и усеченный fingerprint,
   материал ключей никогда не логируется.
6. Поддерживается ротация KEK с перепаковкой DEK
   (`POST /api/admin/crypto/rewrap-deks`) — `docs/key-rotation.md`.
7. Доступ к записям — только владельцу; чужая запись неотличима от
   несуществующей (единый 404, тесты `E2eFlowIT.*`). Административные
   операции — только роль `ADMIN` (SecurityConfig + `@PreAuthorize` +
   проверка в сервисе).

Ошибка расшифровки возвращает нейтральный ProblemDetail (RFC 7807) без
деталей; стектрейсы клиентам не возвращаются.

## CSV export/import: риски и mitigations

Экспорт сейфа в формате Chrome Password Manager CSV — намеренная фича для
миграции в Chrome/другой сейф (см. README, раздел «Сейф — CSV
Export/Import»): `GET /api/vault/export` и
`GET /api/admin/users/{id}/vault/export` отдают CSV c **паролями в
открытом виде**. Это даёт пользователю возможность мигрировать свои данные,
но создаёт дополнительные риски, не покрываемые обычной моделью «секреты
никогда не покидают БД в открытом виде».

> Относитесь к экспортированному CSV-файлу как к **резервной копии сейфа**:
> не передавайте по незащищённым каналам, не храните в открытом виде,
> удаляйте сразу после миграции. На каждом export-ответе выставляется
> заголовок `X-Vault-Export-Warning: csv-contains-plaintext-passwords` —
> его можно использовать в мониторинге/алертах.

### Угрозы и mitigations

#### 1. Утечка экспортированного файла

**Угроза**: потеря ноутбука/флешки с CSV, утечка из общего бакета/S3/Google
Drive, отправка файла в чат/на почту, копирование в шару — раскрытие
**всех паролей** пользователя одной выгрузкой.

**Mitigations**:

- TLS обязателен при download'е: HTTP-трафик к API запрещён; reverse proxy
  терминирует TLS и принудительно редиректит HTTP → HTTPS
  (`docs/deployment.md` §5). На стороне приложения включается
  `Strict-Transport-Security` (`APP_HSTS_ENABLED=true` за TLS-терминацией).
- `Cache-Control: no-store` уже стоит на всех ответах, включая export —
  файл не сохраняется в кэшах reverse proxy/браузера.
- Документированная рекомендация пользователям: **удалять CSV сразу после
  миграции**, хранить только в зашифрованных бэкапах, не передавать
  сторонним сервисам. Это зафиксировано в README и в самом export-ответе
  (заголовок-предупреждение).
- Регулярная ротация паролей в записях сейфа снижает долгосрочный ущерб
  от компрометации конкретного файла.

#### 2. Перехват по сети при отсутствии TLS

**Угроза**: download CSV по HTTP/прокси без TLS — перехват паролей на
участке клиент↔сервер.

**Mitigations**:

- Приложение работает по HTTP за reverse proxy; развёртывание без TLS
  запрещено политикой проекта (`AGENTS.md`, `docs/deployment.md`).
- Заголовок `X-Vault-Export-Warning` на export-ответах позволяет
  интеграторам/мониторингу ловить случаи обращения к export и алертить
  при подозрительном источнике.
- HSTS включается за TLS-терминацией: браузер/API-клиент после первого
  успешного HTTPS-контакта отказывается ходить на тот же хост по HTTP.

#### 3. Случайный импорт в чужой аккаунт (admin)

**Угроза**: администратор импортирует CSV в чужой аккаунт через
`POST /api/admin/users/{id}/vault/import` (ошибся идентификатором, выбрал
не того пользователя) — перезапись/дубли чужих записей.

**Mitigations**:

- Эндпоинт `/api/admin/users/{id}/vault/import` требует роль `ROLE_ADMIN`
  на уровне `SecurityConfig` + `@PreAuthorize` + проверка в сервисе
  (defense in depth); обычный пользователь не имеет доступа.
- `{id}` проверяется на существование: несуществующий пользователь →
  `404` ProblemDetail без побочных эффектов.
- Импорт по умолчанию идёт со стратегией `skip` — повторный импорт того же
  файла не перезаписывает существующие записи; для перезаписи нужен
  явный `conflictStrategy=upsert`.
- `dryRun=true` перед боевым импортом: отчёт покажет, какие записи
  были бы созданы/обновлены/пропущены, без реальных изменений в БД.
- Аудит `VAULT_IMPORTED` фиксирует `actor`, `target` (идентификатор
  пользователя), `strategy`, `csvSha256`, счётчики `created/updated/skipped/failed` —
  по аудиту можно восстановить, кто и что именно импортировал, и в какой
  аккаунт.

#### 4. Случайный upsert старыми/чужими паролями в свой аккаунт

**Угроза**: пользователь импортирует с `conflictStrategy=upsert` старый
CSV (например, из бэкапа или из другого сейфа) — **перезапись** текущих
паролей старыми значениями.

**Mitigations**:

- Дефолт `conflictStrategy=skip` — повторный импорт не перезаписывает
  существующие записи. Для перезаписи нужен явный выбор.
- `dryRun=true` доступен и для своих, и для admin-импортов: позволяет
  увидеть отчёт `wouldCreate` / `wouldUpdate` / `skipped` до применения.
- `failFast=false` по умолчанию — ошибки валидации отдельных строк
  собираются в `errors[]`, импорт не прерывается на первой проблемной
  строке; пользователь видит полный отчёт.
- Действия после такого инцидента — `docs/runbook.md`,
  «Восстановление после случайного импорта».

#### 5. DoS через импорт больших файлов

**Угроза**: импорт очень большого CSV — нагрузка на CPU (расшифровка +
перешифровка DEK под каждую запись), память, долгие транзакции.

**Mitigations**:

- Жёсткий лимит размера файла: `MAX_CSV_BYTES` (по умолчанию 10 МиБ);
  превышение — `413`/`422` ProblemDetail.
- Лимит числа записей в экспорте: `MAX_EXPORT_ROWS` (по умолчанию
  10 000); экспорт большего числа записей — `413`/`422`.
- Rate-limit на `POST /api/vault/import` и admin-вариант: 3 запроса в
  минуту с одного IP
  (`app.vault.import.rate-limit.{window-seconds:60, max-requests:3}`);
  превышение — `429` ProblemDetail с заголовком `Retry-After`.
- `failFast=false` гарантирует, что одна плохая строка не «зациклит»
  импорт на повторной валидации.

### Аудит и наблюдаемость

Все успешные и неуспешные операции экспорта/импорта пишутся в аудит:

- `VAULT_EXPORTED` — actor (кто запросил), target (себя или чужой
  аккаунт через admin), число строк, `csvSha256` (для отслеживания,
  какой именно файл был выдан; без секретов);
- `VAULT_IMPORTED` — actor, target, стратегия (`skip`/`upsert`), флаг
  `dryRun`, счётчики `created/updated/skipped/failed`, `csvSha256`,
  ошибки валидации (без содержимого строк).

В `details` аудита **никогда не пишутся** пароли, номера карт, секреты
из CSV, полный текст файла. По аудиту можно восстановить, кто и когда
выполнял экспорт/импорт и с какими счётчиками, но не содержимое
записей.

## Что делать при утечке (БД / логов / данных)

Определите источник, затем действуйте по `docs/threat-model.md`
(матрица реагирования). Кратко:

**Утечка дампа БД.**

1. Дамп сам по себе не раскрывает секреты (только шифротекст), но инцидент:
   ограничьте распространение, зафиксируйте факты.
2. Выполните **ротацию KEK** (`docs/key-rotation.md`): новый ключ →
   перезапуск → `POST /api/admin/crypto/rewrap-deks`. После перепаковки
   украденный дамп окончательно бесполезен для новых данных.
3. Отзовите все пользовательские токены (сброс паролей администратором).
4. Расследуйте канал утечки; пересмотрите шифрование бэкапов (`age`/`gpg`,
   `docs/backup-restore.md`).

**Утечка логов.**

1. Логи не содержат секретов по построению (запрещено и подтверждено
   тестами; `SensitiveDataMasker` — последний рубеж), но проверьте выгрузку
   на неожиданные артефакты (stack trace с данными, отладочные строки).
2. Ревизия того, куда и кто имеет доступ к системе логирования; те же
   требования хранения, что к БД.
3. Если в логах все же найден секрет (например, кто-то нарушил правило) —
   считайте его скомпрометированным: смените соответствующий пароль/ключ.

**Утечка файла секрета на хосте** — см. следующий раздел
(компрометация KEK) или смену пароля БД (`POSTGRES_PASSWORD` +
`docker compose up -d db` + перезапуск app).

## Что делать при компрометации мастер-ключа

Это максимальный по ущербу инцидент: держатель KEK + дамп БД может
расшифровать все записи. Действовать немедленно:

1. **Изолировать**: ограничить доступ к хосту/хранилищу, где жил ключ;
   не удалять скомпрометированный ключ из конфигурации до перепаковки DEK.
2. **Аварийная ротация KEK** (детали — `docs/key-rotation.md`,
   раздел «Аварийная ротация»):
   - сгенерировать новый KEK (`./scripts/generate-master-key.sh`);
   - добавить его в конфигурацию как активный
     (`APP_CRYPTO_KEYS_<N>_ACTIVE=true`), старый оставить как
     `ACTIVE=false` только для расшифровки;
   - перезапустить приложение;
   - `POST /api/admin/crypto/rewrap-deks` — перепаковать все DEK;
   - убедиться в чтении контрольных записей (`reveal=true`).
3. **Отозвать все токены** пользователей (admin-сброс паролей) — компрометация
   KEK часто сопровождает более широкую компрометацию хоста.
4. **Сменить пароль БД** и проверить целостность данных/аудита на предмет
   посторонних действий (вдруг KEK украли вместе с доступом к API).
5. **Бэкапы**: дампы, снятые до ротации, остаются читаемыми с украденным
   KEK — пересмотреть их хранение/сроки или перешифровать хранилище бэкапов.
6. Расследование: источник утечки ключа (логирование, дампы памяти,
   доступ администраторов, утечка из хранилища секретов) и закрытие канала.
7. Аудит ротации: `KEY_ROTATION_STARTED/COMPLETED/FAILED` — убедиться,
   что перепаковка прошла полностью (`rewrappedUsers: 0` при повторном
   вызове).

## Смежные правила (кратко)

- Ошибки API — RFC 7807 ProblemDetail без стектрейсов.
- Все входные данные валидируются `jakarta.validation`.
- Секреты — только из env/файлов секретов/KMS; в коде, репозитории,
  миграциях и артефактах сборки их нет.
- Аудит фиксирует вход/неудачный вход, выпуск/отзыв токена, операции над
  записями, админ-действия и ротацию ключей — без секретов.

## CSV export/import (web и REST) — риски и меры (Фаза 5)

| Риск | Мера |
|---|---|
| CSV содержит plaintext-пароли | Заголовок `X-Vault-Export-Warning` на всех экспортах; `Cache-Control: no-store` (web и REST); data-confirm в UI; предупреждение в README |
| Утечка CSV-строк в логи/аудит | Аудит пишет только агрегаты (entryCount/csvSha256/created/...); парс-ошибки не содержат ячеек файла; проверяется `ObservabilitySecurityIT` (web-экспорт/импорт с маркерным паролем) |
| Массовая запись через импорт | Rate-limit бакета `import` (429 + Retry-After): REST по IP, web — по username сессии (fallback IP); cumulative-cap: существующие записи + строки файла не больше 10 000 — консервативный пре-чек до обработки (skip реально прирастит меньше; dryRun показывает тот же отказ) |
| Oversized-загрузки | `resolve-lazily: true` — Spring-резолвер бросает `MaxUploadSizeExceededException` у контроллера: REST — 413 ProblemDetail (ApiExceptionHandler), web — PRG-flash; Tomcat error-page (`ErrorPageConfig` → `/web/error/file-too-large`, 413) — страховка для падения в фильтрах; окно 10–11 МБ закрывает сервисный `PayloadTooLargeException` |
| Open-redirect через Referer | `WebExceptionAdvice.safeReturnTo`: same-origin + путь `/web/...` + запрет `//` и `:` — иначе fallback (unit-покрыто) |
| Повторный импорт по F5 | PRG: отчёт во flash, GET `/report`; повторный GET без flash → редирект на форму |
| «Осиротевшие» теги при откатах | TagInsertHelper (REQUIRES_NEW): тег может закоммититься без привязки — безвреден, удаляется через `/web/tags` |

### Дополнительные замечания (fix-волна фазы 5)

- **Восстановление большого сейфа**: залить сейф обратно через CSV-импорт при
  более чем ~5000 существующих записях невозможно — cumulative-cap считает
  все строки файла против лимита 10 000 (включая дубликаты при skip).
  Восстановление большого сейфа — только из бэкапа БД
  (`docs/backup-restore.md`).
- **rateLimitFilter до CsrfFilter** (web-цепочка) — осознанный трейд-офф:
  CSRF-флуд с кукой жертвы сжигает её import-квоту (DoS одного аккаунта
  приемлемее, чем обход лимита), альтернативный порядок открывал бы обход
  бакета запросами без CSRF-токена.
- **dryRun считается в лимите импорта** (3 запроса / 60 с по умолчанию):
  проверочные прогоны не бесплатны — это защита от разведки через dryRun.
- **TOCTOU cumulative-cap**: пре-чек не атомарен с применением (между count
  и insert возможен параллельный импорт). Смягчения: rate-limit (максимум
  3 запроса на пользователя в окне) и ограниченный blast-radius — прямое
  следствие только собственный сейф (или сейф target у админа).
