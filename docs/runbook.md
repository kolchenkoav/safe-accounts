# Runbook безопасных счетов (safe-accounts)

Операционная шпаргалка дежурного/администратора. Подробности — в
`docs/deployment.md`, `docs/security.md`, `docs/key-rotation.md`,
`docs/backup-restore.md`.

## 1. Как посмотреть здоровье

```bash
# Общее состояние (liveness/readiness для оркестратора):
curl -fsS http://localhost:8080/actuator/health
# {"status":"UP"}
curl -fsS http://localhost:8080/actuator/health/liveness
curl -fsS http://localhost:8080/actuator/health/readiness

# Состояние контейнеров compose:
docker compose ps

# Метрики Prometheus (только агрегаты, без секретов):
curl -fsS http://localhost:8080/actuator/prometheus | head
```

Compose-healthcheck приложения уже построен на `/actuator/health`.
Остальные actuator-эндпоинты (`env`, `beans`, `mappings`, ...) закрыты
(denyAll), `show-details: never` — наружу ничего лишнего.

Если `status: DOWN` — проверьте, что контейнер БД здоров (`docker compose ps`,
healthcheck `pg_isready`) и что KEK доступен (приложение падает на старте без
мастер-ключа — это ожидаемое поведение).

## 2. Как посмотреть логи

```bash
docker compose logs app --tail=200 -f
docker compose logs db  --tail=100
```

Что можно и чего нельзя ожидать в логах (зафиксировано тестами и
`SensitiveDataMasker`):

- Разрешено: имена пользователей, key id и усеченный fingerprint KEK,
  счетчики rewrap, коды ошибок, IP (rate limiter).
- Запрещено и отсутствует: пароли, мастер-ключ, DEK, Bearer-токены,
  расшифрованные секреты; тела запросов не логируются.

Журнал аудита (бизнес-события) смотрите не в логах, а в БД/через API:

```bash
curl -s "http://localhost:8080/api/admin/audit?type=LOGIN_FAILURE&page=0&size=50" \
  -H "Authorization: Bearer $admin_token"
```

## 3. Как сделать бэкап

```bash
./scripts/backup.sh
# backups/safe_accounts_<db>_<YYYYMMDD>_<HHMMSS>.dump (pg_dump -Fc, права 0600)
```

Переменные: `COMPOSE_PROJECT_NAME`, `BACKUP_DIR`, `POSTGRES_DB`,
`POSTGRES_USER`. Полная инструкция, шифрование дампов (`age`/`gpg`) и правила
хранения KEK отдельно от дампов — `docs/backup-restore.md`.

## 4. Как восстановиться

```bash
# Приложение скрипт остановит сам на время восстановления:
./scripts/restore.sh backups/<файл>.dump          # с подтверждением
./scripts/restore.sh backups/<файл>.dump --force  # для автоматизации
```

Требования: тот же KEK (`VAULT_MASTER_KEY_BASE64`), тот же compose-проект.
**Обязательная проверка после восстановления**: прочитать контрольную запись
сейфа через API (`GET /api/vault/<id>?reveal=true`) или UI («Показать пароль»)
— механический успех `pg_restore` не считается успехом. Полный DR-сценарий на
чистой машине — `docs/backup-restore.md` §2.

## 5. Как отозвать токены

**Один пользователь отзывает свой текущий токен** (logout):

```bash
curl -X POST http://localhost:8080/api/auth/logout -H "Authorization: Bearer $token"
```

**Все токены пользователя** (при подозрении на кражу): администратор делает
сброс пароля — он отзывает все токены пользователя:

```bash
curl -X POST http://localhost:8080/api/admin/users/<userId>/reset-password \
  -H "Authorization: Bearer $admin_token" -H 'Content-Type: application/json' \
  -d '{"newPassword":"<новый пароль ≥12 символов>"}'
```

Пользователь может сам отозвать остальные свои токены сменой пароля
(`POST /api/me/password` — текущий токен сохраняется, остальные отзываются).
Аудит: `TOKEN_REVOKED` / `USER_RESET_PASSWORD`.

## 6. Как создать администратора

**Вариант A — bootstrap при пустой БД** (первый запуск): задайте
`APP_ADMIN_USERNAME` и `APP_ADMIN_PASSWORD` в окружении; при старте на пустой
БД будет создан первый администратор с ролью `ROLE_ADMIN`. Повторный запуск
ничего не перезаписывает. Пароль не логируется.

**Вариант B — через админ-API** (уже есть администратор):

```bash
curl -X POST http://localhost:8080/api/admin/users \
  -H "Authorization: Bearer $admin_token" -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"Str0ng-Passw0rd!","role":"ADMIN"}'
```

Доступ к `/api/admin/**` — только роль `ADMIN` (SecurityConfig +
`@PreAuthorize` + проверка в сервисе). Обычная регистрация
(`POST /api/auth/register`) всегда создает пользователя без админ-прав.

## 7. Как ротировать ключ

Кратко (полный процесс с проверками — `docs/key-rotation.md`):

1. `./scripts/generate-master-key.sh` — новый KEK.
2. Добавить в конфигурацию как активный
   (`APP_CRYPTO_KEYS_<N>_ID/SECRET_BASE64/ACTIVE=true`), **старый ключ
   не удалять** (`ACTIVE=false`).
3. `docker compose restart app`.
4. `POST /api/admin/crypto/rewrap-deks` (Bearer-токен администратора) —
   идемпотентно, повторный вызов возвращает `rewrappedUsers: 0`.
5. Проверить чтение контрольных записей (`reveal=true`).
6. Старый ключ удалить только после завершения перехода **и** истечения срока
   старых бэкапов.

Аудит ротации: `KEY_ROTATION_STARTED` / `KEY_ROTATION_COMPLETED` /
`KEY_ROTATION_FAILED` (только key id и счетчики).

## 8. Восстановление после случайного импорта

Импорт CSV в формате Chrome (см. README, «Сейф — CSV Export/Import»)
может привести к повреждению данных при неправильной стратегии или
неправильном файле. Ниже — три типовых сценария и порядок действий.

### Сценарий 1. Пользователь импортировал старый/чужой CSV со стратегией `upsert`

**Симптом**: пользователь сообщает, что часть его паролей в записях сейфа
заменена старыми значениями (или значениями из другого источника). В
аудите — свежее событие `VAULT_IMPORTED` с `strategy=upsert` от его имени.

**Порядок действий**:

1. **Посмотреть аудит** — определить масштаб повреждения:

   ```bash
   curl -s "http://localhost:8080/api/admin/audit?type=VAULT_IMPORTED&userId=<userId>&from=<ts>&to=<ts>&page=0&size=50" \
     -H "Authorization: Bearer $admin_token" | jq
   ```

   В ответе — `actor`, `target`, `strategy`, `csvSha256`,
   счётчики `created`/`updated`/`skipped`/`failed`, ошибки валидации.
   По этим данным видно, какие записи были фактически перезаписаны.

2. **Если есть свежий backup БД до момента импорта** —
   `./scripts/backup.sh` сохраняет дампы в `backups/`
   (`docs/backup-restore.md`). Восстановить через `scripts/restore.sh`:

   ```bash
   ./scripts/restore.sh backups/safe_accounts_<db>_<YYYYMMDD>_<HHMMSS>.dump --force
   ```

   Скрипт идемпотентен, останавливает app на время восстановления и
   проверяет дамп (`pg_restore --list`); требуется **тот же** KEK.
   После восстановления обязательно прочитать контрольную запись
   (`reveal=true`) — механический успех `pg_restore` не считается
   успехом.

3. **Если backup нет** — попробовать восстановить данные из самого CSV:

   - по `csvSha256` в аудите найти у пользователя исходный CSV-файл
     (пользователь должен иметь его локально; если нет — запросить
     повторный экспорт из источника, из которого делался импорт, например
     `chrome://password-manager/settings → Export`);
   - если у пользователя сохранился **правильный** CSV (с актуальными
     паролями) — сделать повторный импорт этого файла с
     `conflictStrategy=upsert` (он вернёт записи в нужное состояние);
   - если правильного CSV нет — попросить пользователя пройтись по
     пострадавшим записям вручную и **ввести новые пароли** через
     `PUT /api/vault/{id}` или web UI; старые значения восстановить
     невозможно.

4. **Зафиксировать инцидент**: задокументировать, какие записи были
   перезаписаны (из аудита `csvSha256` + счётчик `updated`), и
   попросить пользователя сменить **пароль пользователя** —
   `POST /api/me/password` (`docs/security.md`, раздел «Как защищены
   токены доступа»): это отзовёт все прочие токены и закроет
   потенциально скомпрометированные сессии.

### Сценарий 2. Admin импортировал CSV в чужой аккаунт

**Симптом**: при просмотре аудита — `VAULT_IMPORTED` с `actor=<admin>` и
`target=<userId>`, не совпадающим с владельцем файла; либо пользователь
сообщает о неожиданных записях в своём сейфе.

**Порядок действий**:

1. **Аудит** — найти событие:

   ```bash
   curl -s "http://localhost:8080/api/admin/audit?type=VAULT_IMPORTED&userId=<userId>&page=0&size=50" \
     -H "Authorization: Bearer $admin_token" | jq
   ```

   По `csvSha256` и счётчикам `created`/`updated`/`skipped`/`failed`
   определить, какой именно файл попал в чужой аккаунт и в каком объёме
   произошли изменения.

2. **Если есть свежий backup БД до инцидента** —
   `scripts/restore.sh` (см. сценарий 1, шаг 2). Помните: восстановление
   **откатывает всю БД**, а не только пострадавшего пользователя —
   выполняйте его только если прочие пользователи согласны на откат
   (или пострадавший пользователь изолирован в отдельный кластер).

3. **Если backup нет** — связаться с владельцем пострадавшего аккаунта:

   - объяснить, что произошло (без раскрытия содержимого CSV и без
     секретов из аудита);
   - попросить его **пройтись по своим записям** и заменить пароли
     через `PUT /api/vault/{id}` или web UI;
   - **отозвать все токены** пострадавшего пользователя:
     `POST /api/admin/users/<userId>/reset-password` (отзывает все
     токены пользователя, новый пароль пользователь задаёт сам);
   - рекомендовать пользователю сменить пароли в связанных внешних
     сервисах (поскольку импорт мог перезаписать их старыми значениями
     из чужого CSV).

4. **Если admin-аккаунт подозревается в компрометации** (CSV взят
   непонятно откуда, admin действовал не по инструкции) — выполнить
   **аварийную ротацию KEK** (`docs/key-rotation.md`,
   «Аварийная ротация»): скомпрометированный admin с доступом к БД и
   аудиту теоретически мог получить материал ключа через побочные
   каналы. Дополнительно — сменить пароль admin-пользователя, отозвать
   все admin-токены, проверить аудит на посторонние действия от его
   имени.

### Сценарий 3. Утечка экспортированного CSV-файла

**Симптом**: пользователь сообщает, что CSV-экспорт попал в чужие руки
(потерял ноутбук/флешку, отправил не тому адресату, файл утек из общего
бакета/S3/Google Drive). В аудите — свежее `VAULT_EXPORTED` от его имени.

**Порядок действий**:

1. **Отозвать все токены пользователя** — закрыть текущие сессии и
   доступ через API:

   ```bash
   # Самостоятельно (пользователь):
   curl -X POST http://localhost:8080/api/me/password \
     -H "Authorization: Bearer <token>" -H 'Content-Type: application/json' \
     -d '{"oldPassword":"<старый пароль>","newPassword":"<новый пароль ≥12 символов>"}'
   # Текущий токен сохраняется, остальные отзываются.
   ```

   ```bash
   # Через администратора (надёжнее — отзывает ВСЕ токены, включая текущий):
   curl -X POST http://localhost:8080/api/admin/users/<userId>/reset-password \
     -H "Authorization: Bearer $admin_token" -H 'Content-Type: application/json' \
     -d '{"newPassword":"<новый пароль ≥12 символов>"}'
   ```

   Подробности и связанные аудит-события (`PASSWORD_CHANGED`,
   `USER_RESET_PASSWORD`, `TOKEN_REVOKED`) — `docs/security.md`
   («Как защищены токены доступа») и §5 настоящего runbook.

2. **Рекомендовать пользователю сменить ВСЕ пароли в записях сейфа** —
   раз файл утек, все пароли в CSV скомпрометированы. Смена через
   `PUT /api/vault/{id}` (новый `password` для каждой записи) или
   web UI. Каждая смена фиксируется в аудите как `SECRET_UPDATED`.

3. **Проверить аудит на подозрительные действия** от имени пользователя
   в период между экспортом и инцидентом:

   ```bash
   curl -s "http://localhost:8080/api/admin/audit?userId=<userId>&from=<exportTime>&page=0&size=200" \
     -H "Authorization: Bearer $admin_token" | jq
   ```

   Особое внимание: `SECRET_REVEALED`, `VAULT_EXPORTED`,
   `VAULT_IMPORTED`, `LOGIN_SUCCESS` с незнакомых IP. Если обнаружены
   следы использования токена или файла — расширить инцидент по
   `docs/threat-model.md` (компрометация токена, утечка БД).

4. **При подозрении на компрометацию DEK** (например, злоумышленник
   имел не только CSV, но и доступ к БД) — выполнить **аварийную
   ротацию KEK** (`docs/key-rotation.md`, «Аварийная ротация»)
   с последующей перепаковкой всех DEK через
   `POST /api/admin/crypto/rewrap-deks`. Без этого украденный CSV
   остаётся валидным и после смены паролей пользователем (CSV — это
   снимок старых паролей на момент экспорта).

5. **Сменить пароль пользователя** (`POST /api/me/password` или admin-сброс)
   — как в шаге 1: даже если токены были отозваны ранее, смена пароля
   закрывает оставшиеся риски переиспользования украденной сессии и
   фиксируется в аудите как `PASSWORD_CHANGED`.

### Превентивные меры

- Импортируйте CSV **только после `dryRun=true`** — отчёт покажет, какие
  записи будут созданы/перезаписаны, без реальных изменений.
- Не используйте `conflictStrategy=upsert` для файлов, в которых вы не
  уверены; дефолт — `skip`.
- Храните экспортированные CSV только в зашифрованных хранилищах,
  удаляйте сразу после миграции.
- Для регулярных миграций между экземплярами `safe-accounts`
  используйте JSON-экспорт (`vault-export.json`, планируется —
  отдельная фича), а не Chrome-CSV.

## Быстрая справка по инцидентам

| Симптом | Действие | Раздел |
|---|---|---|
| Приложение не стартует | Проверить KEK (`VAULT_MASTER_KEY_*` / `APP_CRYPTO_KEYS_*`) и БД | §1, `deployment.md` |
| 429 на login/register | Ожидаемо: rate limit; проверить источник в аудите | §2, `threat-model.md` |
| 429 на `/api/vault/import` | Ожидаемо: 3 импорта/мин с IP; подождать или сменить IP | §8, `security.md` |
| Подозрение на кражу токена | Сброс пароля пользователя (отзывает все токены) | §5 |
| Подозрение на компрометацию KEK | Аварийная ротация ключа + отзыв токенов | §7, `key-rotation.md`, `security.md` |
| Потеря KEK | Восстановление из бэкапа ключа (отдельное хранилище) | `backup-restore.md` §3 |
| Случайный импорт (`upsert`) своим/чужим CSV | Аудит → restore → ручная правка → смена пароля | §8 (сценарии 1, 2) |
| Утечка экспортированного CSV | Отзыв токенов → смена всех паролей в сейфе → аудит → ротация KEK при компрометации DEK | §8 (сценарий 3), `security.md` |

## Восстановление после случайного импорта CSV (Фаза 5)

1. **Оценить масштаб**: в аудите найти `VAULT_IMPORTED` (detailsJson:
   `actor`, `target`, `csvSha256`, `totalRows`, `created`, `updated`,
   `strategy`, `dryRun`). `csvSha256` идентифицирует конкретный файл.
2. **Что произошло**: `skip` — ничего не перезаписывалось (только новые записи);
   `upsert` — существующие записи с тем же (site, login) перезаписаны
   (включая пароль) старыми IV заменить на новые; удалений не бывает.
3. **Откат**: точечный откат невозможен (записи перешифрованы) — использовать
   бэкап БД (`docs/backup-restore.md`). Перед массовым импортом делайте экспорт
   или запускайте `dryRun` (отчёт покажет created/updated без изменений).
4. **Профилактика**: импорт под rate-limit (429), файл ≤10 МБ, суммарный
   лимит 10 000 записей (консервативный пре-чек).

Заметки: «лимит 10 МБ» — это `MAX_CSV_BYTES`; контейнерный multipart-буфер —
11 МБ (окно 10–11 МБ закрывается сервисным 413/flash). PRG-контракт: браузер
всегда следует 302 и потребляет flash-отчёт; два POST без follow-GET возможны
только у не-браузерных клиентов. REQUIRES_NEW-трейд-офф TagInsertHelper: тег,
созданный в отдельной транзакции, может остаться без привязки при откате
внешней — удаляется через `/web/tags`.

- Восстановление сейфа с ~5000+ записей через CSV-импорт невозможно
  (cumulative-cap считает все строки файла против лимита 10 000) — только
  бэкап БД (см. `docs/backup-restore.md`).
