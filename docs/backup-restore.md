# Резервное копирование и аварийное восстановление (Task-08)

Этот документ — инструкция администратора safe-accounts по резервному копированию БД,
восстановлению после сбоя и обращению с мастер-ключом (KEK).

## Модель данных и why it matters

В базе `safe_accounts` хранятся **только зашифрованные** секреты:

- пароль каждой записи сейфа шифруется индивидуальным ключом пользователя (**DEK**)
  по алгоритму **AES-256-GCM** с уникальным IV на каждую операцию;
- DEK хранится в БД **только в wrapped-виде** — зашифрованным мастер-ключом (**KEK**);
- KEK **никогда не хранится в БД**: он приходит из окружения
  (`VAULT_MASTER_KEY_BASE64` или файл по пути `VAULT_MASTER_KEY_FILE`).

Следствие:

- дамп БД **сам по себе не раскрывает секреты** — без KEK это набор wrapped-данных;
- **потеря KEK делает восстановление бесполезным**: данные останутся в БД, но
  расшифровать их будет невозможно. Поэтому мастер-ключ — самый ценный актив.

## 1. Как сделать резервную копию

### Что бэкапится

`scripts/backup.sh` делает логический дамп PostgreSQL (PostgreSQL 16) в **custom-формате**
`pg_dump -Fc` (сжатый, восстанавливается через `pg_restore`). Дамп снимается **внутри
контейнера БД** (`docker exec ... pg_dump`), поэтому версия `pg_dump` всегда совпадает
с версией сервера. Скрипт:

- создаёт каталог `backups/` (если его нет — не падает);
- кладёт файл вида `backups/safe_accounts_<db>_<YYYYMMDD>_<HHMMSS>.dump`
  (имя содержит временную метку);
- ставит на файл права `0600` (только владелец);
- поддерживает переопределение имени проекта и каталога через переменные окружения;
- **не содержит и не печатает секретов** (hardcoded секретов в скриптах нет).

### Команды

```bash
# Бэкап дефолтного проекта (docker compose name: safe-accounts)
./scripts/backup.sh

# Свой compose-проект и каталог дампов
COMPOSE_PROJECT_NAME=prod BACKUP_DIR=/var/backups/safe-accounts ./scripts/backup.sh
```

Переменные окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `COMPOSE_PROJECT_NAME` | `safe-accounts` | имя compose-проекта (скрипт ищет контейнер `<project>-db-1`) |
| `BACKUP_DIR` | `./backups` | куда складывать дампы (создаётся автоматически) |
| `POSTGRES_DB` | `safe_accounts` | имя базы данных |
| `POSTGRES_USER` | `postgres` | пользователь БД |

Дамп содержит wrapped-секреты всех пользователей — обращайтесь с файлом как с
конфиденциальными данными (права 0600, хранение на зашифрованном томе, off-site копия).

### Опционально: шифрование бэкапа

Task-08 допускает шифрование дампа через `age` или `gpg` — это **опциональный** пункт.
Самый простой вариант (шифруем уже снятый дамп на хосте):

```bash
# age: публичный ключ получателя, приватный ключ хранится ОТДЕЛЬНО от бэкапа
./scripts/backup.sh && age -r age1<recipient-public-key> -o backups/dump.age backups/<файл>.dump && shred -u backups/<файл>.dump

# GPG: шифрование на публичный ключ администратора
./scripts/backup.sh && gpg --encrypt --recipient admin@example.com backups/<файл>.dump
```

Не храните ключ расшифровки дампа на той же машине/в том же хранилище, что и дамп.

## 2. Как восстановить БД

`scripts/restore.sh <файл-дампа> [--force]` восстанавливает дамп в целевую БД в контейнере:

1. проверяет наличие и не-пустоту файла дампа;
2. проверяет, что контейнер БД существует и запущен;
3. проверяет, что целевая БД существует, и что файл — корректный дамп
   (пробное чтение `pg_restore --list`);
4. **останавливает контейнер приложения** (`<project>-app-1`), чтобы на время
   восстановления приложение не работало с наполовину восстановленными данными;
5. выполняет `pg_restore --clean --if-exists --no-owner --no-privileges`:
   - `--clean --if-exists` — повторный запуск идемпотентен (объекты пересоздаются);
   - `--no-owner --no-privileges` — объекты создаются от целевого пользователя БД
     (как в docker-compose из Task-07).

```bash
./scripts/restore.sh backups/safe_accounts_safe_accounts_20260101_120000.dump
# без интерактивного подтверждения (для runbook/автоматизации):
./scripts/restore.sh backups/<файл>.dump --force
```

Переменные окружения — те же, что у `backup.sh` (`COMPOSE_PROJECT_NAME`,
`POSTGRES_DB`, `POSTGRES_USER`).

**Если БД восстановлена в новый пустой кластер:** перед запуском приложения создайте БД,
например `docker compose up -d db` с нужным `POSTGRES_DB` — compose создаст базу при
первом старте контейнера postgres. Затем запускайте `restore.sh`.

### Восстановление на «чистую» машину (полный DR-сценарий)

```bash
# 1. Чистая БД
docker compose -p restore-dr up -d db
# 2. Дождаться healthcheck, затем восстановить дамп
COMPOSE_PROJECT_NAME=restore-dr ./scripts/restore.sh backups/<файл>.dump --force
# 3. Приложение с тем же мастер-ключом
VAULT_MASTER_KEY_BASE64=<тот же KEK> docker compose -p restore-dr up -d app
```

## 3. Где хранить мастер-ключ

**Главное правило: мастер-ключ хранится отдельно от дампа БД. Держать KEK вместе с
бэкапом БД в одном открытом месте запрещено** — тогда скомпрометированный бэкап сразу
раскрывает все секреты, и вся модель шифрования теряет смысл.

Требования к хранению KEK:

- KEK живёт в **отдельном** защищённом хранилище: внешний KMS/Vault, менеджер секретов,
  HSM или как минимум — зашифрованный файл на отдельной машине/носителе с ограниченным
  доступом (в проде это `VAULT_MASTER_KEY_FILE` на отдельном томе или переменная
  окружения оркестратора).
- **Должен существовать отдельный процесс бэкапа мастер-ключа**: копия KEK снимается
  отдельно от БД, хранится в другом месте (другой физический носитель/хранилище), и
  наличие этой копии **регулярно проверяется** (например, раз в квартал — тестовое
  восстановление + расшифровка одной записи).
- Нельзя хранить KEK:
  - в репозитории, в коде, в логах, в артефактах сборки;
  - в том же каталоге/томе/хранилище, что и дампы БД;
  - в открытом виде на той же машине, где лежат дампы.
- При ротации KEK (Task-06, `POST /api/admin/crypto/rewrap-deks`) **старый KEK нужно
  сохранять** до окончания ротации: он нужен для расшифровки DEK, обёрнутых старым
  ключом. Мультиключевая схема (`APP_CRYPTO_KEYS_N_*`) поддерживает несколько KEK —
  активный ровно один, старые остаются для дешифровки.
- Удалять старый KEK можно только после завершения ротации **и** истечения срока
  всех бэкапов, снятых до ротации (см. `docs/key-rotation.md`, шаг 7).

## 4. Как проверить успешность восстановления

Восстановление считается успешным, если **приложение работает и записи читаются**.
Механическая проверка `pg_restore` (без ошибок) — необходимое, но не достаточное условие.

Порядок проверки (сценарий из Task-08, «Тестирование процесса»):

1. **До аварии**: создайте тестовую запись сейфа (через UI/API: `POST /api/vault/entries`
   с сайтом, логином, паролем, примечанием).
2. Снимите бэкап: `./scripts/backup.sh`.
3. Разверните чистую БД (см. «Восстановление на чистую машину» выше).
4. Восстановите дамп: `./scripts/restore.sh backups/<файл>.dump`.
5. Запустите приложение с **тем же мастер-ключом**, что использовался при создании записи
   (`VAULT_MASTER_KEY_BASE64` или `VAULT_MASTER_KEY_FILE`).
6. Убедитесь, что:
   - `/actuator/health` отвечает `UP`;
   - вход пользователя работает (`POST /api/auth/login`);
   - `GET /api/vault/entries` возвращает тестовую запись (сайт, логин, примечание —
     без пароля, как и положено списку);
   - `GET /api/vault/entries/{id}` возвращает **расшифрованный пароль** — это главный
     признак: DEK успешно расwrapлен тем же KEK.

Быстрая автоматизированная проверка (пример, вместо шагов 6.x):

```bash
# список записей (пароль не возвращается)
curl -s -H "Authorization: Bearer <token>" http://localhost:8080/api/vault/entries
# детальная запись с расшифрованным паролем
curl -s -H "Authorization: Bearer <token>" http://localhost:8080/api/vault/entries/<id>
```

Если после восстановления `GET /api/vault/entries/{id}` не расшифровывает пароль —
почти всегда причина в **несовпадении мастер-ключа** (см. «Типичные ошибки»).

## 5. Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Приложение падает на старте: мастер-ключ не найден / невалиден | `VAULT_MASTER_KEY_BASE64`/`VAULT_MASTER_KEY_FILE` не заданы или файл не читается; в недефолтном (не-тестовом) профиле приложение обязано падать без ключа | Задайте ключ из хранилища KEK, проверьте путь/переменную, перезапустите |
| Приложение стартует, но `GET /api/vault/entries/{id}` не возвращает пароль / ошибка расшифровки | Восстановление выполнено с **другим** KEK (ключ другой среды, после ротации без сохранения старого) | Используйте KEK, соответствующий дампу; при ротации — настройте `APP_CRYPTO_KEYS_N_*` со старыми ключами |
| `pg_restore` падает с ошибками зависимостей/дублей | Дамп восстанавливался без `--clean` во вторую попытку, или в целевой БД уже есть объекты | Скрипт использует `--clean --if-exists`; при ручном восстановлении повторите с этими флагами |
| `backup.sh`: «Контейнер БД не найден» | Неверный `COMPOSE_PROJECT_NAME` (контейнер ищется как `<project>-db-1`) | Укажите имя проекта явно: `COMPOSE_PROJECT_NAME=<имя> ./scripts/backup.sh` |
| `restore.sh`: «БД не существует» | Целевая БД не создана в чистом кластере | `docker compose up -d db` с нужным `POSTGRES_DB` (создаст базу), затем повторить `restore.sh` |
| Дамп восстановлен, но пользователи не могут войти | Пользователи и хэши паролей (Argon2id) лежат в той же БД — если восстановили **другой** дамп, учётные данные прежние | Восстановите нужный дамп; хэши паролей переносятся вместе с БД |
| Потерян мастер-ключ | KEK не бэкапился отдельно от БД | **Восстановление бесполезно** — данные в БД не расшифровать. Единственная защита — заранее настроенный отдельный процесс бэкапа KEK |

## Сводка: что бэкапить и где это хранить

| Актив | Чем бэкапим | Где храним |
|---|---|---|
| БД (schema + данные) | `scripts/backup.sh` (pg_dump -Fc) | Отдельное хранилище дампов, off-site копия |
| Мастер-ключ (KEK) | Отдельный процесс (вне `backup.sh`) | Отдельное хранилище секретов, **не** вместе с дампами |

## Ключевые инварианты (безопасность прежде удобства)

1. Дамп БД без KEK не раскрывает секреты — но и не является самодостаточным бэкапом.
2. KEK без дампа БД бесполезен; дамп без KEK бесполезен. Нужны **оба**, в **разных**
   местах, с независимыми процессами бэкапа.
3. В скриптах нет hardcoded секретов; все параметры — из окружения.
