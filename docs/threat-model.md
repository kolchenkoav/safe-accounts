# Модель угроз safe-accounts

Документ описывает доверенные границы, активы и сценарии угроз (STRIDE-подобный
перебор ключевых рисков) с существующими мерами защиты и остаточными рисками.
Соответствует правилам `AGENTS.md`: безопасность важнее удобства, компромиссы
указаны явно.

## Доверенные границы и активы

```
[Клиент (браузер/API)] ⇄ TLS ⇄ [Reverse proxy] ⇄ [app (Spring Boot)]
                                                       ⇄ (JDBC) ⇄ [PostgreSQL]
[Окружение/секреты: KEK, пароль БД] --- вне БД, вне репозитория
```

Ключевые активы:

| Актив | Где живет | Защита |
|---|---|---|
| Пароли пользователей | БД, только Argon2id-хэш | Argon2id (m=64МиБ, t=3, p=1), plaintext нигде не хранится |
| Bearer-токены | БД, только SHA-256 хэш | выдача один раз, TTL 24 ч, ревокация/отзыв |
| Секреты сейфа (сайт/логин/пароль/примечание) | БД, только шифротекст AES-256-GCM | DEK каждого пользователя, уникальный IV на операцию |
| DEK пользователей | БД, только wrapped KEK-ом | AES-256-GCM, `dek_kek_id` |
| Мастер-ключ (KEK) | Только окружение/файл секретов | отсутствует в БД и коде; без него приложение не стартует |
| Аудит | БД (`audit_events`) | только нечувствительные данные |

Доверенная граница «хост/оркестратор»: KEK и пароль БД считаются находящимися
вне границы приложения — компрометация хоста выводит из строя все меры ниже
(см. остаточные риски).

## Сценарии угроз

### 1. Утечка БД (дамп украден)

**Сценарий**: злоумышленник получил дамп `safe_accounts` (SQL-инъекция на другом
сервисе с доступом к БД, скомпрометированный бэкап, инсайдер).

**Меры**:

- Все чувствительные поля (`vault_entries.site_enc/login_enc/password_enc/
  notes_enc`, `users.dek_wrapped`) — только шифротекст AES-256-GCM; plaintext
  отсутствует (тесты `SecurityChecksIT.*`).
- Пароли — Argon2id-хэш; токены — SHA-256 хэш (сырой токен не восстановим).
- KEK в БД отсутствует физически → без KEK дамп бесполезен для расшифровки.

**Остаточный риск**: онлайновый перебор слабых паролей пользователей по
Argon2id-хэшам. Требование к политике паролей (≥12 символов) снижает, но
не устраняет. Факт утечки БД = инцидент: ротация KEK (см. ниже) делает
украденный дамп окончательно нечитаемым после перепаковки DEK.

### 2. Утечка логов

**Сценарий**: логи приложения выгружены в SIEM/S3/через ошибку конфигурации.

**Меры**:

- Запрещено и не реализовано логирование: паролей, мастер-ключа, DEK,
  токенов, расшифрованных секретов; тела запросов не логируются.
- `SensitiveDataMasker` — «последний рубеж»: типовые чувствительные поля
  (`password`, `token`, `secret`, `authorization`) маскируются в сообщениях
  об ошибках (unit-тесты `SensitiveDataMaskerTest`).
- В крипто-логах только key id и усеченный SHA-256 fingerprint.
- Аудит не пишет расшифрованные секреты (тест
  `VaultApiIT.vaultEventsAreAuditedWithoutSecrets`).

**Остаточный риск**: логи содержат имена пользователей, IP и id записей —
метаданные, не секреты. Рекомендация: те же требования хранения/шифрования
к центральной системе логов, что и к БД.

### 3. Компрометация токена (кража Bearer-токена)

**Сценарий**: токен перехвачен в сети или скопирован с машины клиента.

**Меры**:

- Токен показывается клиенту один раз при выпуске; в БД только хэш.
- TTL 24 ч; явная ревокация `POST /api/auth/logout`; отзыв всех токенов
  при смене пароля (`POST /api/me/password`) и при admin-сбросе
  (`POST /api/admin/users/{id}/reset-password`).
- Rate limiting на login/register (429 + `Retry-After`), блокировка аккаунта
  после 5 неудачных попыток на 15 минут.
- Веб-интерфейс не использует Bearer-токены вообще: серверные HTTP-сессии
  (HttpOnly cookie) + CSRF; токены не попадают в `localStorage`.

**Рекомендации**: работа только за TLS (`APP_HSTS_ENABLED=true` за
терминацией), при подозрении на кражу — смена пароля пользователем (мгновенно
отзывает остальные токены) или сброс пароля администратором.

### 4. Компрометация мастер-ключа (KEK)

**Сценарий**: KEK прочитан с хоста, из хранилища секретов или у администратора.

**Последствия**: злоумышленник вместе с дампом БД может распаковать все DEK
и расшифровать все записи. Это максимальный ущерб по модели.

**Меры / реагирование**:

1. Немедленная аварийная ротация KEK (см. `docs/key-rotation.md`, раздел
   «Аварийная ротация»): новый ключ → перезапуск → rewrap DEK.
2. После перепаковки скомпрометированный KEK бесполезен для новых данных.
3. Отзыв всех пользовательских токенов (сброс паролей).
4. Расследование источника утечки; проверка бэкапов: дампы, снятые до
   ротации, останутся читаемыми с украденным KEK — их срок жизни/шифрование
   пересматривается (шифрование дампов `age`/`gpg` — см.
   `docs/backup-restore.md`).

**Остаточный риск**: данные, зашифрованные до ротации и попавшие к
злоумышленнику до неё, защищены не будут. KEK храните в KMS/Vault/HSM,
а не в `.env` на общем хосте.

### 5. Брутфорс логина

**Сценарий**: перебор паролей через `POST /api/auth/login` или веб-форму.

**Меры**:

- Rate limiting по IP (скользящее окно, по умолчанию 10 запросов/60 с,
  `429` + `Retry-After`, Task-09) на API и веб-логин.
- Блокировка аккаунта на 15 минут после 5 неудачных входов.
- Нейтральные сообщения об ошибке (не раскрывают, существует ли пользователь).
- Argon2id делает офлайн-перебор по хэшам дорогим.
- Аудит: `LOGIN_FAILURE` — источник для алертинга SIEM.

**Остаточный риск**: in-memory лимитер действует per-instance — при
горизонтальном масштабировании нужен распределенный лимитер (Redis).
Распределенная бот-сеть растягивает перебор по IP — помогает блокировка
по аккаунту.

### 6. Потеря ключа (KEK)

**Сценарий**: хранилище KEK утеряно/повреждено, ключ не восстановим.

**Последствия**: необратимая потеря всех секретов сейфа — DEK не распаковать,
данные в БД останутся навсегда зашифрованными «в никуда». Это худший исход
для доступности.

**Меры**:

- Отдельный процесс бэкапа KEK: копия хранится **отдельно от дампов БД**
  (другой носитель/хранилище), регулярная проверка восстановимости
  (тестовая расшифровка контрольной записи — раз в квартал).
- Мультиключевой режим: до завершения ротации старый KEK остается
  в конфигурации — удалять до истечения срока старых бэкапов запрещено
  (`docs/key-rotation.md`, шаг 7).

**Компромисс**: хранение KEK вне БД требует дисциплины внешнего бэкапа
ключа; приложение сознательно не хранит «эскейп-копию» KEK — это сделало бы
бессмысленной всю модель шифрования (безопасность > удобство).

### 7. Ошибка восстановления из бэкапа

**Сценарии**: дамп поврежден, восстановлен не в ту БД, восстановление без
правильного KEK, приложение стартовало на полувосстановленных данных.

**Меры** (`scripts/restore.sh`, детали в `docs/backup-restore.md`):

- Скрипт проверяет дамп (`pg_restore --list`), наличие и запуск контейнера БД,
  существование целевой БД; идемпотентен (`--clean --if-exists`).
- На время восстановления контейнер приложения останавливается.
- Восстановление обязательно с **тем же** KEK (`VAULT_MASTER_KEY_BASE64`).
- Процедура проверки успешности: механический успех `pg_restore`
  недостаточен — обязательна проверка чтения контрольной записи сейфа через
  API/UI (reveal пароля) после запуска приложения.
- Регулярная репетиция DR (тестовое восстановление на чистой машине).

**Остаточный риск**: человеческая ошибка (не тот дамп/не та БД) — снижается
разделением окружений и именованием дампов с временной меткой.

## Матрица реагирования

| Угроза | Приоритет | Первое действие | Документ |
|---|---|---|---|
| Утечка БД | высокий | ротация KEK + расследование | `key-rotation.md`, `security.md` |
| Утечка логов | средний | проверка маскирования, ревизия логов | `security.md` |
| Кража токена | средний | смена/сброс пароля (отзыв токенов) | `runbook.md` |
| Компрометация KEK | критический | аварийная ротация + отзыв токенов | `key-rotation.md` |
| Брутфорс | средний | блокировка, алерт по `LOGIN_FAILURE` | `runbook.md` |
| Потеря KEK | критический | восстановление из бэкапа ключа | `backup-restore.md` |
| Ошибка восстановления | высокий | повторное восстановление, контрольная запись | `backup-restore.md` |
