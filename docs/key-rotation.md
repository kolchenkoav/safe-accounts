# Ротация мастер-ключа (KEK)

Процесс плановой ротации мастер-ключа (KEK) для safe-accounts. DEK пользователей
перепаковывается активным KEK через эндпоинт
`POST /api/admin/crypto/rewrap-deks` (реализация — `AdminService.rewrapDeks`,
Task-06). Процедура **онлайн**: приложение продолжает работать, полного
перешифрования записей сейфа не требуется (записи шифруются DEK, а не KEK).

Схема ключей:

- **KEK** (мастер-ключ, AES-256) — приходит из окружения
  (`VAULT_MASTER_KEY_BASE64` / `VAULT_MASTER_KEY_FILE` или
  `APP_CRYPTO_KEYS_N_*`); в БД никогда не хранится.
- **DEK** — индивидуальный AES-256 ключ каждого пользователя; в БД только
  в wrapped-виде (`users.dek_wrapped`, `dek_iv`, `dek_kek_id`).
- Поддерживается **мультиключевой режим** (`APP_CRYPTO_KEYS_N_ID` /
  `APP_CRYPTO_KEYS_N_SECRET_BASE64` / `APP_CRYPTO_KEYS_N_ACTIVE`):
  активный ровно один, остальные — только для расшифровки.

> Требования к роли: только `ADMIN` (`/api/admin/**`, defense in depth:
> SecurityConfig + `@PreAuthorize` + проверка в сервисе).

## Шаг 1. Сгенерировать новый мастер-ключ

```bash
./scripts/generate-master-key.sh
```

Скрипт печатает base64-ключ (32 байта). Передайте значение по защищенному
каналу в хранилище секретов (KMS/Vault/файл секретов на отдельном томе) —
не в чат, не в репозиторий, не в логи.

## Шаг 2. Добавить новый ключ в конфигурацию как активный

Мультиключевой режим — рекомендуемый способ (позволяет держать старый ключ
для расшифровки одновременно с новым активным):

```dotenv
APP_CRYPTO_KEYS_1_ID=kek-2026
APP_CRYPTO_KEYS_1_SECRET_BASE64=<новый ключ из шага 1>
APP_CRYPTO_KEYS_1_ACTIVE=true

APP_CRYPTO_KEYS_0_ID=kek-2024
APP_CRYPTO_KEYS_0_SECRET_BASE64=<старый ключ, пока НЕ удалять>
APP_CRYPTO_KEYS_0_ACTIVE=false
```

Правила:

- `APP_CRYPTO_KEYS_N_ID` — нечувствительный идентификатор (он попадает в БД
  в `dek_kek_id` и в логи как key id; материал ключа — никогда).
- Активный ключ **ровно один** (`ACTIVE=true`) — иначе приложение падает
  на старте (проверка в `KeyManager`).
- Для legacy-режима (одиночный `VAULT_MASTER_KEY_BASE64`) активным становится
  этот ключ; старый должен остаться доступным через `APP_CRYPTO_KEYS_*`.

## Шаг 3. Оставить старый ключ доступным для расшифровки

Не удаляйте старый `APP_CRYPTO_KEYS_N_*` из конфигурации: DEK части
пользователей все еще завернуты старым KEK, и без него rewrap завершится
ошибкой (409 ProblemDetail), а расшифровка записей станет невозможной.

## Шаг 4. Перезапустить приложение

```bash
docker compose restart app
# или: docker compose up -d --force-recreate app
curl -fsS http://localhost:8080/actuator/health
```

При старте `KeyManager` загрузит оба ключа; в логах появятся только key id
и усеченный SHA-256 fingerprint — материала ключей в логах не бывает.

## Шаг 5. Выполнить перепаковку DEK

```bash
admin_token=$(curl -s -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<пароль администратора>"}' | jq -r .accessToken)

curl -s -X POST http://localhost:8080/api/admin/crypto/rewrap-deks \
  -H "Authorization: Bearer $admin_token"
# {"rewrappedUsers": 42, "activeKekId": "kek-2026"}
```

Свойства операции:

- **Идемпотентна**: пользователи, чей DEK уже завернут активным KEK,
  пропускаются; повторный вызов безопасен.
- Каждый пользователь коммитится отдельно (`saveAndFlush`): при сбое уже
  перепакованные сохраняются, операцию можно повторить.
- Если старый KEK недоступен — понятная ошибка 409 ProblemDetail без деталей
  шифрования.
- Аудит: `KEY_ROTATION_STARTED` / `KEY_ROTATION_COMPLETED` /
  `KEY_ROTATION_FAILED` (в деталях только key id, счетчики и actor — без
  секретов). Проверить: `GET /api/admin/audit?type=KEY_ROTATION_COMPLETED`.

## Шаг 6. Убедиться, что данные читаются

1. Убедитесь, что `rewrappedUsers` равен числу пользователей со старым
   `dek_kek_id` (после повторного вызова возвращается `rewrappedUsers: 0` —
   это норма и подтверждает идемпотентность).
2. Через API владельца прочитайте запись сейфа:

   ```bash
   curl -s "http://localhost:8080/api/vault/<entryId>?reveal=true" \
     -H "Authorization: Bearer $user_token"
   ```

   Расшифрованный пароль должен совпасть с ожидаемым (каждый reveal
   фиксируется в аудите как `SECRET_REVEALED`).
3. Проверьте контрольную запись через веб-интерфейс (кнопка «Показать
   пароль»).
4. (Опционально) Проверьте в БД, что `users.dek_kek_id` у всех пользователей
   равен новому key id:

   ```sql
   SELECT dek_kek_id, count(*) FROM users GROUP BY dek_kek_id;
   ```

## Шаг 7. Удалить старый ключ (после завершения перехода)

Удаляйте старый `APP_CRYPTO_KEYS_N_*` из конфигурации **только когда**:

- rewrap завершен и повторный вызов возвращает `rewrappedUsers: 0`;
- выборочная проверка расшифровки записей успешна (шаг 6);
- **истек срок жизни всех бэкапов, снятых до ротации** — старые дампы
  содержат DEK, завернутые старым KEK, и без него невосстановимы.

Удаление: убрать блок `APP_CRYPTO_KEYS_<старый>_…` из `.env`/хранилища
секретов и перезапустить `app`. Если политикой организации предписано
сохранять ключи дольше (например, бэкапы хранятся год) — держите старый KEK
в хранилище секретов дольше, пометив как «retired, только расшифровка»
(`ACTIVE=false`). Это компромисс в пользу возможности восстановления старых
бэкапов.

После удаления старого ключа повторите проверку шага 6 на контрольных
записях.

## Аварийная ротация (при подозрении на компрометацию KEK)

Процесс тот же, но: (1) новый ключ генерируется и вводится немедленно,
(2) rewrap выполняется сразу после перезапуска, (3) старый ключ не удаляется
до завершения rewrap, но доступ к нему максимально ограничивается,
(4) все токены пользователей отзываются (`POST /api/auth/logout` каждым
пользователем либо сброс пароля администратором —
`POST /api/admin/users/{id}/reset-password` отзывает все токены),
(5) детали — в `docs/security.md` («Что делать при компрометации
мастер-ключа») и `docs/runbook.md`.
