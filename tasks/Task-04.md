# Task-04: Пользователи, аутентификация и токены

## Цель
Реализовать пользователей, вход, выпуск и отзыв токенов, а также базовую защиту от перебора.

## Результат
- Есть регистрация/создание пользователя
- Есть логин
- Есть Bearer-token authentication
- Есть отзыв токена
- Есть аудит входов
- Есть защита от брутфорса

## Функциональные требования

### Пользователи
1. Имя пользователя:
    - уникальное
    - хранится в нижнем регистре
    - валидируется по формату и длине
2. Пароль:
    - минимальная длина 12 символов
    - хэшируется через Argon2id
3. Роли:
    - `ROLE_USER`
    - `ROLE_ADMIN`
4. Статус:
    - `enabled`
    - `disabled`

### Создание пользователя
При создании пользователя:
1. Создается запись в `users`.
2. Генерируется DEK.
3. DEK заворачивается в активный KEK.
4. В БД сохраняется:
    - `dek_wrapped`
    - `dek_iv`
    - `dek_kek_id`

### Bootstrap администратора
Реализовать безопасный первичный запуск:
- если пользователей нет
- и заданы `APP_ADMIN_USERNAME` и `APP_ADMIN_PASSWORD`
- тогда создается первый администратор

Требования:
- пароль из переменной окружения не логируется
- после создания администратора повторный автоматический запуск не должен его перезаписывать

### Аутентификация
Реализовать:
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/me`
- `POST /api/me/password`

### Токены
1. При успешном входе выпускается токен.
2. Токен:
    - криптографически случайный
    - длина не менее 256 бит энтропии
    - формат: префикс + base64url
3. В БД хранится только хэш токена.
4. Токен возвращается клиенту только один раз.
5. Поддержка:
    - срок действия
    - отзыв
    - последнее использование
    - привязка к пользователю

### Защита от перебора
Минимально:
- после 5 неудачных попыток блокировать пользователя на 15 минут
- фиксировать неудачные входы в аудит

Опционально:
- rate limiting по IP в Task-09

## Security-требования
1. Сессия для API — stateless.
2. CSRF для API отключен, так как используется Bearer token.
3. Все endpoint'ы, кроме логина и служебных health, требуют аутентификации.
4. Запрещено возвращать клиенту хэши, токены других пользователей и служебные детали.
5. При смене пароля отзывать все токены пользователя, кроме текущего (по решению реализации).

## Аудит
Писать события:
- `LOGIN_SUCCESS`
- `LOGIN_FAILURE`
- `TOKEN_ISSUED`
- `TOKEN_REVOKED`
- `USER_CREATED`
- `USER_DISABLED`
- `USER_ENABLED`
- `PASSWORD_CHANGED`

В аудит не писать:
- пароль
- токен
- секреты сейфа

## Тесты
1. Успешный логин возвращает токен.
2. Неверный пароль возвращает ошибку.
3. Заблокированный пользователь не может войти.
4. Токен дает доступ к защищенным endpoint'ам.
5. Отозванный токен больше не работает.
6. Чужой пользователь не может получить доступ к `/api/me` под чужим токеном.
7. При создании пользователя создается wrapped DEK.

## Критерии приемки
1. Аутентификация работает через Bearer token.
2. В БД нет открытых паролей и токенов.
3. Есть аудит.
4. Есть защита от перебора.
5. Все новые интеграционные тесты проходят.
