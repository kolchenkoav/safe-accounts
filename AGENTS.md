# AGENTS.md

## Назначение проекта
Проект `safe-accounts` — это серверное приложение-сейф для надежного хранения учетных записей:
- сайт
- логин
- пароль
- примечание

Приложение должно быть безопасным, пригодным для эксплуатации в Docker и устойчивым к типовым рискам:
- утечка базы данных
- логирование секретов
- несанкционированный доступ
- отсутствие резервных копий
- компрометация токенов доступа

## Глобальные правила для агентов
1. Язык реализации: **Java 21**.
2. Framework: **Spring Boot 3.3.x**.
3. База данных: **PostgreSQL 16**.
4. Миграции: **Flyway**.
5. Все изменения схемы БД — только через Flyway.
6. `spring.jpa.hibernate.ddl-auto` в проде всегда `validate`.
7. Запрещено хранить секреты в коде, репозитории, логах, миграциях или артефактах сборки.
8. Запрещено логировать:
    - пароли пользователей
    - мастер-ключ
    - DEK
    - токены доступа
    - расшифрованные пароли учетных записей
9. Запрещено использовать:
    - MD5
    - SHA-1 для парольных хэшей
    - ECB
    - детерминированные или повторно используемые IV
    - самописные небезопасные схемы шифрования
10. Все секреты конфигурации читаются только из:
- переменных окружения
- файлов секретов
- внешнего KMS/Vault (если добавлен позже)

## Требования к безопасности
### Пароли пользователей
- Для хэширования пользовательских паролей использовать **Argon2id**.
- Запрещено хранить пароль в открытом виде где-либо.

### Токены доступа
- Аутентификация клиентов — через Bearer-токен.
- В БД хранить только хэш токена.
- Токен показывается клиенту только один раз при выпуске.
- Должна поддерживаться принудительная ревизация и отзыв токенов.

### Шифрование секретов
- Использовать **AES-256-GCM**.
- Для каждого пользователя генерировать собственный **DEK**.
- DEK хранится в БД только в зашифрованном виде (wrapped) мастер-ключом **KEK**.
- IV должен быть уникальным для каждой операции шифрования и генерироваться через `SecureRandom`.
- Запрещено хранить секреты в открытом виде в БД.

### Мастер-ключ
- Мастер-ключ должен задаваться из окружения или файла секрета.
- Если мастер-ключ отсутствует в профиле, отличном от тестового, приложение должно падать на старте.
- Запрещено печатать мастер-ключ в логи.
- Допустимо логировать только нечувствительный идентификатор ключа (key id / fingerprint), без материала ключа.

### Доступ к данным
- Пользователь имеет доступ только к своим записям.
- Все операции над записями обязаны проверять владельца.
- Административные операции доступны только роли `ADMIN`.

### Аудит
- Аудит фиксирует:
    - вход
    - неудачный вход
    - выпуск токена
    - отзыв токена
    - создание/изменение/удаление записи сейфа
    - административные действия
    - ротацию ключей
- В аудит запрещено писать расшифрованные секреты.

## Требования к API
1. Стиль: REST, JSON.
2. Версионирование через базовый путь `/api`.
3. Ошибки — в формате **RFC 7807 ProblemDetail**.
4. Запрещено возвращать стектрейсы клиенту.
5. Списки записей не должны возвращать пароли по умолчанию.
6. Расшифровка пароля разрешена только в явном детальном запросе при наличии прав.
7. Все входящие данные валидируются через `jakarta.validation`.

## Требования к коду
- Пакет по умолчанию: `com.example.safeaccounts`.
- DTO реализовать как `record`, где это уместно.
- Сущности JPA — отдельные классы.
- Не смешивать доменные сущности и API DTO напрямую.
- Слои:
    - `api`
    - `service`
    - `domain`
    - `repository`
    - `security`
    - `crypto`
    - `audit`
    - `config`
- Сервисный слой содержит бизнес-правила.
- Контроллеры тонкие.

## Требования к тестам
1. Обязательны:
    - unit-тесты для криптографии
    - интеграционные тесты для Flyway/JPA
    - security-тесты для авторизации
    - интеграционные тесты API
2. Использовать **Testcontainers** для PostgreSQL в интеграционных тестах.
3. Тесты не должны требовать реальный внешний сервис.
4. Запрещено использовать боевые секреты в тестах.
5. Допустим отдельный тестовый фиксированный мастер-ключ только в тестовом профиле.

## Требования к миграциям
- Файлы миграций: `V<version>__description.sql`.
- Запрещено менять уже примененные миграции.
- Все индексы и ограничения задаются явно.
- Для чувствительных полей не использовать текстовые комментарии с примерами реальных секретов.

## Требования к Docker
- Образ приложения должен быть многоэтапным.
- В финальный образ не должны попадать исходники и секреты.
- Контейнер должен работать от непривилегированного пользователя.
- Поддержка Docker Compose обязательна.
- В `docker-compose` предусмотреть:
    - отдельный контейнер БД
    - volume для данных БД
    - секреты для пароля БД и мастер-ключа

## Определение готовности задачи
Задача считается выполненной, если:
1. Код компилируется.
2. Все новые тесты проходят.
3. `./mvnw verify` проходит локально.
4. Нет секретов в коде, логах и артефактах.
5. Обновлена документация.
6. Приняты критерии приемки из соответствующего `Task-xx.md`.

## Приоритет при конфликте требований
При конфликте между удобством и безопасностью агент обязан выбрать безопасность и явно описать компромисс в задаче.
